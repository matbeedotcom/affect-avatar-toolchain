# Phase 1 hand-off — what shipped, what Phase 2 + Phase 3 still need

Status as of 2026-05-05.

---

## Phase 1: shipped

The text-only deterministic affect simulator is implemented as a
workspace member crate at [`tools/affect_simulator/`](../../../../tools/affect_simulator/).

- **Language:** Rust. PROJECT_PLAN.md §12 Q1 (Rust vs TypeScript) is
  resolved in favor of Rust to match the runtime; the appraisal /
  dynamics / regulation modules are stateless so Phase 2 can lift them
  into runtime nodes without re-authoring the equations.
- **Modules:** `event`, `state`, `appraisal`, `dynamics`, `regulation`,
  `renderer`, `runner`, plus `affect-sim` CLI.
- **`update_channel`** in `dynamics.rs` is verbatim from PROJECT_PLAN.md
  §6 Phase 1.
- **`derive_core`** in `state.rs` is verbatim from PROJECT_PLAN.md.
- **Scenarios:** all 12 canonical (§7) authored as JSON under
  [`scenarios/`](../../../../tools/affect_simulator/scenarios/).
- **Acceptance tests:** 9 tests in
  [`tests/scenarios.rs`](../../../../tools/affect_simulator/tests/scenarios.rs)
  cover determinism, decay-to-baseline, the safety contract
  (`adversarial_provocation` + `safety_dampening_floor = 1.0`), and
  per-scenario expected behavior. All pass.

Quick reproduction:

```bash
cargo run -p affect-simulator -- run-all tools/affect_simulator/scenarios
cargo test -p affect-simulator
```

Verbose review of the Channel B prompt summaries (the same string
Phase 2's prompt-augmentation node will emit):

```bash
cargo run -p affect-simulator -- run \
  tools/affect_simulator/scenarios/repeated_tool_failure.json --verbose
```

## Phase 2: not yet shipped — checklist

The full Phase 2 deliverable (PROJECT_PLAN.md §6 Phase 2) requires
runtime node work:

- [ ] **`crates/core/src/nodes/affect/mod.rs`** — new module under nodes/.
- [ ] **`AffectAppraisalNode`**: imports `AppraisalEngine` from
  `affect-simulator` (or moves the rules into a shared `affect-core`
  crate). Consumes `PerceivedEvent`s, emits `Appraisal`.
- [ ] **`AffectDynamicsNode`**: 200 ms tick, applies `Dynamics::step_*`,
  emits `AffectState`.
- [ ] **`AffectRegulationNode`**: emits `RegulationPolicy`.
- [ ] **`AffectPromptRendererNode`** (`prompt_renderer.rs`): emits the
  Channel B summary string. Renderer logic is `renderer.rs` as-is.
- [ ] **`AffectRouterNode`** (`router.rs`): converts `RegulationPolicy`
  to a `SamplingConfig` override + a system-prompt augmentation. C/D
  channels disabled in Phase 2 (Phase 4 wires them).
- [ ] **`crates/core/src/nodes/llama_cpp/generation.rs`** modification —
  accept a per-turn `sampling_override` aux input (`temperature`,
  `max_tokens`, `top_p`). The Channel A equation in PROJECT_PLAN.md
  §6 Phase 2 lives in `AffectRouterNode`, not in the generation node.
- [ ] **Manifest example:** [`examples/shared-pipelines/affect-pipeline.yaml`](../../../../examples/shared-pipelines/affect-pipeline.yaml)
  is committed as the planning artifact (status `planned-phase-2-3`)
  and documents the eventual node graph. Phase 2 turns it from
  documentation into a runnable pipeline by registering the missing
  node types.
- [ ] **PROJECT_PLAN.md §12 Q4** (structured fields vs natural-language
  prompt): simulator picks structured fields. Confirm with reviewers
  before Phase 2 lands; if natural-language wins, change `renderer.rs`
  in this crate first so simulator and runtime stay aligned.

### Q4 recommendation (optional)

The structured form has two advantages: (1) it deterministically maps
`AffectState → string`, so the same state always produces the same
prompt suffix — easier for reviewers; (2) it resists prompt-injection
better than natural-language paragraphs because the field labels are
not generated by an LLM. Recommend adopting structured fields for
Phase 2; revisit if the LLM under-uses them.

## Phase 3: not yet shipped — checklist

The full Phase 3 deliverable (PROJECT_PLAN.md §6 Phase 3) is unblocked
because:

- Phase 5's `whisper_to_vad_ridge.onnx` exists at
  `tools/affect_calibration/artifacts/`.
- Spike C confirmed encoder access through HF `AutoModelForSpeechSeq2Seq`.
- The simulator already accepts `EventKind::Prosody*` events — see
  `conflicting_signals.json`.

Remaining:

- [ ] **`clients/python/remotemedia/nodes/ml/whisper_transcription.py`**
  — additive change: emit encoder hidden states alongside text on a
  second output channel (`encoder_states`). Spike C's reference code
  is in [`spike-c-whisper-encoder.py`](spike-c-whisper-encoder.py).
- [ ] **`crates/core/src/nodes/audio/mean_pool.rs`** — ~30 LoC:
  `[T_frames × d_whisper] → [d_whisper]` mean-pool. Output type is
  `RuntimeData::tensor` with `TensorType::F32`.
- [ ] **`clients/python/remotemedia/nodes/affect/prosody_vad.py`** —
  Python ONNX-runtime node. Loads
  `whisper_to_vad_ridge.onnx`, runs inference per chunk, thresholds
  V/A predictions to emit `EventKind::ProsodyArousalHigh`,
  `ProsodyValenceNegative`, `ProsodyUncertain`. When the ONNX is
  missing, emits placeholder events with `confidence = 0.1` so the
  pipeline degrades gracefully (PROJECT_PLAN.md §6 Phase 3 acceptance).
- [ ] **Appraisal-rule extension** — already in
  [`tools/affect_simulator/src/appraisal.rs`](../../../../tools/affect_simulator/src/appraisal.rs).
  When the rules are extracted into a shared `affect-core` crate
  during Phase 2, Phase 3 inherits them automatically.

The wiring contract is documented in
[`examples/shared-pipelines/affect-pipeline.yaml`](../../../../examples/shared-pipelines/affect-pipeline.yaml).

## Recommended sequencing

1. **Phase 4 runtime integration** (LFM2-Audio MLX, channels C+D from
   the calibration artifacts) — the highest-leverage next move and
   the user-visible payoff of the Phase 5 work that already shipped.
2. **Phase 2** — once Phase 4 lands, the channel-A/B router has a
   real runtime to emit overrides into. Lifting the simulator's
   appraisal/dynamics/regulation modules into a shared crate is a
   ~half-day refactor.
3. **Phase 3** — straightforward once Phase 2's affect chain is in
   the registry. Phase 5's regressor ONNX is already trained, so the
   `prosody_vad` node is a wrapper job.

This ordering reduces churn: Phase 2's node shape is informed by
what Phase 4 actually consumes (e.g. whether `LFM2AudioMlxNode` wants
a single combined `SteeringDirective` or separate aux ports per
channel). Doing Phase 2 in the abstract risks re-doing it after
Phase 4 lands.
